# The real version — how it works and how to set it up The demo had 14 August baked into the file. The live version has **nothing baked in**: you pick a session, it fetches that night's figures from a data file, and those files are refreshed from the e-commerce database automatically. **No database key ever reaches the browser.** That matters, because the `recon` tables still have row-level security switched off — publishing a key against them would leave the database open to anyone with the link. This design sidesteps that entirely. --- ## What is in `UPLOAD THESE` now ``` index.html the app — no session baked in publish_data.py pulls a date range from the database data/ 19 sessions, 4–17 August index.json sc-2026-08-14.json rwc-2026-08-11.json … etc .github/workflows/refresh-data.yml refreshes the data every morning ``` Upload **all of it**, keeping the folder structure. On the GitHub upload page you can drag the whole `UPLOAD THESE` folder in at once and it will preserve the subfolders. --- ## One-time setup, about five minutes ### 1. Give the Action a database token **Settings → Secrets and variables → Actions → New repository secret** - Name: `SUPABASE_PAT` - Value: your Supabase token The token lives only in GitHub Secrets. It is never in the page, never in the repo, never visible to anyone opening the site. ### 2. Let the Action commit **Settings → Actions → General → Workflow permissions** → **Read and write permissions** → **Save** Without this the refresh runs but cannot push what it finds. ### 3. Prove it works **Actions** tab → **Refresh session data** → **Run workflow**. It pulls the last 45 days and commits anything that changed. After that it runs itself at 08:00 UTC daily — after the late sessions have closed. --- ## What the operator sees Pick hall, date and session. The app fetches that night's file and fills in sales, POS drawers, attendance, seats and the flash schedule. If the night has not been published yet it says so plainly rather than showing another session's figures — a bug that cost us an afternoon. Tested against the published files: | | | |---|---| | SC Friday 14 Aug | $65,608 · attendance 260 · people 294 | | RWC Tuesday 11 Aug | $38,619 · attendance 142 · people 160 | | SC Sunday Afternoon 16 Aug | $6,785 · attendance 24 · people 33 | | Thursday 20 Aug | "not published yet" | --- ## How fresh is it As fresh as the last refresh — daily by default. Change the `cron` line in the workflow for more often, or hit **Run workflow** whenever you want it now. For a session being reconciled the night it happened, run it by hand when the staff sit down. Ninety seconds. --- ## If you need it live to the second That means the app talking to Supabase directly, and there is a hard gate first: **All 14 `recon` tables have row-level security disabled and no policies.** `rls_policies.sql` is written and ready, but it must be applied *before* any key is published. After that you need Supabase Auth accounts and the anon key wired into the page. That work is spelled out in `SPEC-08-Deployment.md`. Nothing above depends on it. --- ## Sharing this URL The build in `UPLOAD THESE` carries **the full 67-person roster** so the Staff tab fills itself for any night.
